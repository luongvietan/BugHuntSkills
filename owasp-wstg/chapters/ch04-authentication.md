# 4.4 Authentication Testing (WSTG-ATHN)

Source: WSTG v4.2 §4.4. Attacks the login surface and everything around it: transport, defaults, lockout, bypass, remember-me, cache, password policy, recovery questions, reset flows, and parallel channels.

## Test list

- **WSTG-ATHN-01 — Credentials transported over encrypted channel.** Objective: catch any credential exchange happening over HTTP. Procedure: proxy all login/session/reset traffic (disable HTTPS-upgrading extensions first); force `http://` on the login URL and POST path — does the page still load and accept the POST?; inspect whether session tokens, reset codes, and login data ever travel plaintext, including redirects that bounce HTTP→HTTPS after submission. Interpretation: a login page reachable and functional over HTTP is a fail even if the POST target is HTTPS; check cookies/remember-me tokens too.
- **WSTG-ATHN-02 — Default credentials.** Objective: find factory or predictable logins. Procedure: fingerprint the stack (INFO-08) → consult vendor docs/default-password lists for admin consoles (routers, WebLogic, Tomcat manager); guess common pairs — `admin`/`administrator`/`root`/`system`/`guest`/`operator`/`super` and `qa`/`test`/`testing` × `password`/`pass123`/`admin`/blank; try org-named combos (`appname/appname`), contact-name patterns from email conventions (`jdoe`), and scan page source/JS for hardcoded checks; check whether new accounts ship predictable passwords never forced to change. Interpretation: default admin creds = full compromise; watch lockout thresholds before spraying.
- **WSTG-ATHN-03 — Weak lockout mechanism.** Objective: verify brute-force resistance without DoS-ing users. Procedure: on a test account you can afford to lock, fire N wrong passwords then a correct one at escalating N (3,4,5…) to find the threshold; check auto-unlock timing; probe CAPTCHA — is it solvable by script, checked via response code only, bypassed by dropping the parameter/cookies, or skipped by calling a later step of the flow? Interpretation: missing/threshold-high lockout or replayable CAPTCHA = brute force viable; note a lockout itself is a DoS vector against real users — report, don't exploit.
- **WSTG-ATHN-04 — Bypassing authentication schema.** Objective: reach authenticated function without valid login. Procedure: try four families — **direct page request** (force-browse deep URLs unauthenticated), **parameter modification** (`authenticated=yes`, `admin=1`, valid session IDs swapped into requests), **session ID prediction** (collect samples, detect linear/partial-change sequences, forge next value), **SQL injection on the form** (`' OR '1'='1`); gray-box: look for type-juggling auth checks like PHP loose-compare (`unserialize()` + `b:1` bool tricks). Interpretation: any page reachable unauthenticated that should require login is a bypass; prediction works when cookie values trend linearly over time.
- **WSTG-ATHN-05 — Vulnerable remember password.** Objective: verify remember-me doesn't endanger the account. Procedure: check whether credentials (vs opaque tokens) sit in cookies or browser storage (CLNT-12); analyze remember-token lifetime — non-expiring tokens are dangerous; verify the feature can't be abused via CSRF/clickjacking to persist attacker sessions. Interpretation: credentials stored client-side even encoded = fail; tokens should be server-issued, expiring, and revocable.
- **WSTG-ATHN-06 — Browser cache weaknesses.** Objective: ensure sensitive pages aren't retained client-side. Procedure: enter data, log out, press Back — do protected pages render?; proxy-review responses for `Cache-Control: no-cache, no-store` (+`must-revalidate`), `Expires: 0`, `Pragma: no-cache` on every page with sensitive content; check the browser cache dirs for stored pages. Interpretation: Back-button revealing authenticated pages post-logout = history/cache flaw; sensitive pages must carry no-store directives.
- **WSTG-ATHN-07 — Weak password policy.** Objective: measure resistance to guessing. Procedure: probe policy by attempting to set — single-charset and tiny-length passwords (`123456`, `Password1`), username-containing passwords; test change frequency limits, history depth (can you cycle back to the original?), reuse rules, min/max length, and whether expiry is forced (NIST/NCSC now advise against). Interpretation: accepting `Password1` or the username itself = weak policy; combine with ATHN-03 for brute-force viability.
- **WSTG-ATHN-08 — Weak security question/answer.** Objective: assess whether Q/A can be guessed, OSINT-ed, or brute-forced. Procedure: enumerate the question pool via registration/reset; classify answers — family-known (maiden name), guessable (favorite color), brute-forcible (teacher's first name), public (favorite movie on social media); check self-generated questions (users pick "1+1?"); test answer lockout (ATHN-03) and how many questions must be answered. Interpretation: any question whose answer lives on Facebook or in a 500-name dictionary is bypassable.
- **WSTG-ATHN-09 — Weak password change/reset.** Objective: subvert change/reset to hit other accounts. Procedure: check — can non-admins reset others' passwords; can the process be manipulated (user param swapped mid-flow, CSRF on change, IDOR on reset token); what does reset require (secret question strength, ATHN-08); is the old password shown or a random token mailed (plaintext return = unhashed storage); does reset confirm via emailed link before invalidating; does change require re-auth? Interpretation: reset token predictable/host-injectable (INPV-17) or change lacking re-auth = account takeover.
- **WSTG-ATHN-10 — Weaker authentication in alternative channel.** Objective: find parallel channels with softer auth. Procedure: enumerate — mobile site/app, accessibility site, country/language variants, partner sites sharing accounts, dev/test/UAT/staging mirrors, desktop apps, call centers, IVR; for each, compare password policy, lockout, enumeration resistance, and transport security vs the main channel. Interpretation: staging sites commonly skip lockout/rate limits — the same creds attack succeeds where prod resists.

## Common findings

Login POST accepted over HTTP; `admin:admin` on a discovered console; lockout absent or only-IP-scoped (bypass via `X-Forwarded-For`); forced-browse to `/admin/*` unauthenticated; predictable reset tokens; Back-button post-logout disclosure; staging channel with no rate limiting.

## Escalation notes

ATHN findings chain: IDNT-04 enumeration → ATHN-02/07 guessing → account; ATHN-09 reset flaws → ATO without creds; ATHN-10 channels feed SSRF (INPV-19) and logic tests (BUSL). An auth bypass via parameter tampering is also evidence for ATHZ-02/03.
