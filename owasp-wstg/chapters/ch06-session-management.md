# 4.6 Session Management Testing (WSTG-SESS)

Source: WSTG v4.2 §4.6. The token lifecycle: creation quality, transport protection, attribute hygiene, fixation, CSRF, termination, timeout, puzzling, hijacking.

## Test list

- **WSTG-SESS-01 — Session management schema.** Objective: prove tokens are unpredictable and opaque. Procedure: **collect** many samples (same + different users, log when/where each cookie is set and what it's for — spreadsheet it); **reverse-engineer** structure — embedded meaning (user IDs, timestamps, roles), patterns, linear sequences, partial-change fields, weak charset/length (statistical analysis; Burp Sequencer); check for sensitive data or crypto inside the token itself vs server-side reference; **manipulate** — alter unsigned fields, brute-force predictable space, overflow long values. Interpretation: meaningful content or predictable sequences in the token = forgeable sessions.
- **WSTG-SESS-02 — Cookie attributes.** Objective: verify attribute/prefix hardening. Procedure: review each `Set-Cookie` — `Secure` (HTTPS-only transit), `HttpOnly` (JS can't read — limits XSS session theft), `Domain` (unset defaults to host; `mydomain.com` shares with all subdomains — takeover risk), `Path` (`/` shares across sibling apps), `Expires`/`Max-Age` (persistent vs session; reasonable lifetimes), `SameSite` (`Strict`/`Lax`/`None`+Secure — CSRF posture), prefixes `__Host-`/`__Secure-`. Interpretation: missing Secure or overly broad Domain/Path widens theft surface; missing HttpOnly turns XSS into instant ATO.
- **WSTG-SESS-03 — Session fixation.** Objective: catch tokens not rotated at login. Procedure: record the pre-auth cookie; authenticate; check for a *new* token — none issued = fixable. Then the forced-cookie test (needs two accounts): plant attacker-known cookies into the victim session (only meaningful without full HSTS or on cookies lacking integrity/`__Host-`/`__Secure-` prefixes), victim logs in, attacker replays the planted cookie. Interpretation: no rotation at authentication + attacker-injectable cookie = impersonation.
- **WSTG-SESS-04 — Exposed session variables.** Objective: keep session data off plaintext channels and caches. Procedure: swap `https`→`http` mid-session — does the app still serve/track the same Session ID (it shouldn't reuse the secure one on the insecure side)?; examine every request/response carrying the ID for cache directives (`Cache-Control: no-cache` won't protect `Private`-only on shared proxies; add `Expires: 0`, `max-age=0`; HTTP/1.0 caches ignore Cache-Control — need `Pragma: no-cache`); check IDs in URLs (leak via Referer/logs). Interpretation: Session ID over HTTP, in URL, or cacheable = exposable to proxies/shared machines.
- **WSTG-SESS-05 — Cross-Site Request Forgery.** Objective: find state changes replayable cross-origin. Procedure: enumerate state-changing requests; check defenses — anti-CSRF token present? validated server-side? tied to session? SameSite on session cookie? Referer/Origin checked? Then attack: drop the token param, supply another account's token, empty it; remove Referer; switch POST→GET; build the auto-submitting PoC (`<img>` for GET, auto-form for POST). Interpretation: if the action completes without a valid unpredictable token and SameSite isn't Strict, it's CSRF — impact scales with the victim's role.
- **WSTG-SESS-06 — Logout functionality.** Objective: verify logout actually kills the session server-side. Procedure: confirm logout UI present/visible on every page; record cookies, invoke logout, then — request a protected page (Back button shows cache, *reload* hits server — must fail); if the cookie was reassigned, **restore the old value and replay** — still valid = server-side state never cleared; test SSO nuances (app logout may not kill IdP session and vice versa). Interpretation: cookie replay after logout = session resurrection; cookie-only frameworks (e.g., ASP.NET forms auth) are prone.
- **WSTG-SESS-07 — Session timeout.** Objective: confirm a server-enforced idle timeout exists. Procedure: wait past the claimed timeout, replay the token — must be invalid; verify timeout tracked server-side, not via client data (cookie timestamps forgeable); check token destruction after timeout (replay = fail); judge length vs data sensitivity (~15 min banking vs longer forums). Interpretation: no timeout or client-computed timeout = replayable sessions; balance usability vs sensitivity.
- **WSTG-SESS-08 — Session puzzling (variable overloading).** Objective: abuse session vars reused across contexts. Procedure: enumerate session variables and where they're set vs consumed; reach *entry points* that populate identity-ish vars (password-recovery page setting `user` context), then hit *exit points* that trust them (account pages) — skipping intended order; try jumping multi-phase flows by pre-seeding later-phase vars. Interpretation: same session var meaning two things lets you bypass auth gates; gray-box code review finds these far faster than black-box luck.
- **WSTG-SESS-09 — Session hijacking.** Objective: demonstrate theft-feasible cookies for network attackers (skip under full HSTS). Procedure: two accounts — victim and attacker. Login as victim; delete every cookie that couldn't leak over HTTP (no HSTS: delete all `Secure` cookies; partial HSTS: delete `Secure` or non-`Domain` cookies); snapshot the rest; trigger a secure function — succeeds = cookies left were enough (note which). Clear jar, login as attacker, write victim's cookies back one by one, re-trigger the function, check victim account for the effect. Interpretation: unprotected cookies carrying session weight = hijackable; partial HSTS + Domain-scoped cookies = leak via plaintext subdomain requests.

## Common findings

Sequential/encoded (not encrypted) session IDs; missing `HttpOnly`+`Secure` on session cookie; `Domain=` too broad; no token rotation at login; CSRF token absent or unvalidated on POSTs; logout = client-side cookie delete only; no idle timeout; recovery flow pre-seeding session identity (puzzling).

## Escalation notes

Session bugs multiply other findings: XSS (INPV-01/02, CLNT-01) + missing HttpOnly = instant session theft; subdomain takeover (CONF-10) + broad Domain cookie = harvest sessions; CSRF (SESS-05) chains with stored XSS for wormable attacks; fixation + phishing = ATO. Session puzzling often unlocks pages that then expose IDOR (ATHZ-04) or logic flaws (BUSL-06).
