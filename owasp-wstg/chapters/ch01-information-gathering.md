# 4.1 Information Gathering (WSTG-INFO)

Source: WSTG v4.2 §4.1. The reconnaissance category — everything learnable before firing active probes. Output of this phase is the input inventory (endpoints, params, tech stack, roles) that drives all later categories. Passive work needs no special permission beyond scope; active enumeration (port scans, dir brute-force) does.

## Test list

- **WSTG-INFO-01 — Search engine discovery for info leakage.** Objective: find sensitive design/config data the org exposed directly or via third parties. Procedure: run `site:`/`inurl:`/`intitle:`/`intext:`/`filetype:`/`cache:` dorks across multiple engines (Google, Bing, DuckDuckGo, Shodan, Wayback); try Google Hacking Database categories (footholds, files with passwords, error messages, sensitive directories); check forums and staging/dev mirrors. Interpretation: indexed content the owner never meant public — network diagrams, creds in posts, UAT sites — is a finding; absence just means index hygiene is good.
- **WSTG-INFO-02 — Fingerprint web server.** Objective: determine server type/version for known-vuln matching. Procedure: grab the `Server` banner (`curl -sI`, openssl for TLS); if obfuscated, compare header *ordering* (Date→Server→… vs Server→Date→…) and trigger default error pages with malformed requests (`GET / SANTA CLAUS/1.1`); confirm with Netcraft/Nikto/nmap. Interpretation: header ordering and stock error pages leak the server even when banners are scrubbed — a version match feeds CVE lookup.
- **WSTG-INFO-03 — Review webserver metafiles.** Objective: mine metadata files for hidden paths and functionality. Procedure: pull `/robots.txt` (Disallow entries = places to look), `sitemap.xml` chains, `/.well-known/security.txt` (contact + policy, useful for reporting), `humans.txt`, `<meta>` tags (`robots`, generator, og:*). Interpretation: Disallow paths aren't secrets but are unadvertised surface; security.txt tells you where findings go.
- **WSTG-INFO-04 — Enumerate applications on webserver.** Objective: find all apps on the host, not just the obvious one. Procedure: attack three axes — non-standard base URLs (`/url1` vs `/`), non-standard ports (`nmap -Pn -sT -sV -p0-65535`), virtual hosts (Host-header enumeration, reverse-IP/DNS services, `site:` results). Interpretation: admin panels and forgotten apps on odd ports/vhosts are the highest-value finds; what you can't enumerate, assume exists.
- **WSTG-INFO-05 — Review webpage content for leakage.** Objective: extract intel from HTML/JS the server ships. Procedure: grep responses for `<!--` comments (SQL, IPs, test creds), meta author/generator tags, DTD doctypes; pull all JS files and hunt hardcoded API keys, internal routes, IPs, secrets; look for `.map` source-map files that de-obfuscate minified code. Interpretation: a leaked key or hidden route converts recon directly into access — verify source maps by requesting `app.js.map`.
- **WSTG-INFO-06 — Identify application entry points.** Objective: enumerate every place input enters. Procedure: proxy-walk the app logging all requests; catalog GET/POST params, headers (User-Agent, Referer, cookies), file-upload fields, and each request's method/content-type/response shape. Interpretation: each logged parameter is a future injection point — completeness here determines coverage everywhere else.
- **WSTG-INFO-07 — Map execution paths through the application.** Objective: document flows a tester can traverse. Procedure: spider with ZAP/Burp (plus AJAX spider for JS apps), then manually click paths spiders miss (multi-step flows, POSTs); keep a spreadsheet/diagram of page → action → params. Interpretation: spiders miss authenticated and stateful paths — gaps in the map are gaps in test coverage.
- **WSTG-INFO-08 — Fingerprint web application framework.** Objective: identify framework/CMS/components for targeted attacks. Procedure: check `X-Powered-By` and unusual headers (`X-Generator`), framework cookie names (`CAKEPHP`, `laravel_session`, `JSESSIONID`, `phpbb3_`), HTML markers (`wp-content`, meta generator), file extensions (`.php`/`.aspx`/`.do`), stock files/folders (`/readme.html`, `/CHANGELOG.txt`), and error pages; confirm with BlindElephant/Wappalyzer/WhatWeb. Interpretation: a named framework + version unlocks known CVEs, default paths, and framework-specific test payloads.
- **WSTG-INFO-09 — (merged into INFO-08).**
- **WSTG-INFO-10 — Map application architecture.** Objective: infer the infrastructure behind the app. Procedure: start from a single-server assumption, then challenge it — detect firewalls/WAFs (blocked probes, mod_security banners), reverse proxies/caches (header anomalies, timing deltas on repeated requests), load balancers (inconsistent `Date`/server headers, `BIGipServer` cookies), app servers (`JSESSIONID`, differing response headers), auth backends (LDAP/DB hints from login behavior). Interpretation: architecture knowledge tells you where a bug lands — front-end XSS vs backend RCE vs pivot into an internal zone.

## Common findings

Default error pages revealing exact versions; `robots.txt` advertising admin paths; JS files with live API keys; `.git`/`*.map` served publicly; Tomcat/admin consoles on 8080+; vhost-only staging sites; `X-Powered-By` disclosing framework + version.

## Escalation notes

Recon feeds everything: version banners → CVE exploit selection (INFO-02/08); metafile paths → CONF-04 backup hunting and CONF-05 admin enum; entry-point inventory → every INPV test; architecture map → SSRF targets (INPV-19) and IDOR object space (ATHZ-04). A leaked key or staging host usually outperforms a week of fuzzing.
