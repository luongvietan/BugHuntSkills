# 4.10 Business Logic Testing (WSTG-BUSL)

Source: WSTG v4.2 §4.10. Failures of *intended-use* logic — the tests scanners can't run because the rules live in the business, not the parser. Requires understanding the workflow first (INFO-07 map), then breaking its assumptions.

## Test list

- **WSTG-BUSL-01 — Business logic data validation.** Objective: submit logically-invalid data past front-end checks. Procedure: beyond boundary-value checks, attack the *semantics* — data valid in format but wrong in context (SSN of a deceased person, out-of-stock items ordered via a partner-fulfillment path, same-day spend against last-night's balance). Identify handoffs between systems (warehouse→partner, app→payment) and inject at the trust boundary; vary formats/sequences/timing and watch the second system's reaction. Interpretation: format-valid but context-invalid data accepted = logic-validation gap; cross-system trust is where it bites.
- **WSTG-BUSL-02 — Ability to forge requests.** Objective: bypass the GUI to feed the backend unexpected values. Procedure: intercept POST/GETs and hunt — **guessable/predictable values** (incrementing IDs, interval patterns), **hidden features** (debug flags, dev "easter egg" params, `debug=1`, admin screens), replayed one-time values (a `discount=1` flag resent to stack discounts). Interpretation: server honoring forged params, hidden params, or replays = business-rule bypass — the UI was the only control.
- **WSTG-BUSL-03 — Integrity checks.** Objective: submit data the GUI marks non-editable or never offered. Procedure: enumerate hidden fields, disabled inputs, drop-downs, and relational fields; proxy-submit values outside the offered set (another project's name in a dropdown, spouse data for a "single" record, admin-only fields like username+password as a normal user); verify the server performs relational/consistency edits itself rather than trusting "came from a non-editable control"; check log integrity too (can users write/read/erase audit data?). Interpretation: server-side acceptance of never-offered values = missing relational validation — the UI state machine isn't authoritative.
- **WSTG-BUSL-04 — Process timing.** Objective: exploit timing leaks and transaction windows. Procedure: map time-dependent processes — measurable response-time deltas (valid-user vs invalid-user login timing leaks enumeration — see IDNT-04); windows where state is locked (reserved-but-unpaid seats held forever); stale-price windows (order placed, completed hours later at the old quote). Automate probes for precision; diagram the flow and launch prepared requests at the vulnerable transition. Interpretation: exploitable timing = info leak or resource/financial manipulation — classic race and inventory-hoard bugs.
- **WSTG-BUSL-05 — Function usage limits.** Objective: execute capped functions beyond their limit. Procedure: find once-per-X features (single discount per order, N downloads/month, one vote, one coupon); replay them — resend the request, revisit the page after applying, race parallel submissions, reset via account/app state changes. Interpretation: repeatable limited function = direct financial/logic abuse; note whether the check was client-side, per-session, or per-account.
- **WSTG-BUSL-06 — Circumvention of workflows.** Objective: complete transactions out of order or partially. Procedure: from the workflow map, try — skipping steps (jump straight to step N), canceling after side-effects fire (earn loyalty points, then cancel the tender — do points roll back?), re-entering mid-flow with stale state, editing data post-validation (post clean text, then edit-in banned content that only gets checked at creation). Interpretation: side-effects without rollback or validation bound to a single step = workflow bypass.
- **WSTG-BUSL-07 — Defenses against application misuse.** Objective: detect whether the app notices being attacked. Procedure: derived from all other tests — while testing, log whether clearly-malicious sequences (unauthorized file access → `'` injection → method swap → extra/duplicated params → blatant XSS/SQLi strings) trigger any response: changed responses, request blocking, forced logout/lockout, added auth steps, delays, or increased logging. Interpretation: silent acceptance of blatant misuse = no app-layer defense — an environment where attackers operate undetected; localized per-function controls don't count.
- **WSTG-BUSL-08 — Upload of unexpected file types.** Objective: push file types the business rules didn't approve. Procedure: build a "not approved" set (jsp/exe/HTML+script); test each filter layer — client-JS only? Content-Type header only (change it)? extension-only (`.php.jpg`, `.phtml`, case tricks, null-byte)?; check direct URL access to uploaded files; check path handling (ZIPs containing traversal paths that unzip outside target dir); batch-upload bypass. Interpretation: a disallowed type reaching storage — or a benign type with hostile content/paths — = upload-control gap.
- **WSTG-BUSL-09 — Upload of malicious files.** Objective: determine whether *content* of an allowed type is hostile-checked. Procedure: confirm approved types, then weaponize inside them — web shell uploaded inside the webroot where the server executes code (protect your PoC shell: random name, IP restriction — and remove it after); polyglot files (GIFAR-style image+script), content-sniffing confusion, malicious media exploiting parsers, script-carrying SVG/HTML served same-origin; check whether uploads pass IPS/AV/app-level scanning. Interpretation: executable or script-bearing file reachable via URL = RCE/stored-XSS path; "type was allowed" is not a defense when content isn't inspected.
- **WSTG-BUSL-10 — Test payment functionality.** *(Added post-v4.2 in live WSTG — not in the frozen v4.2 PDF.)* Objective: verify payment flows can't be manipulated to pay less, pay nothing, or gain value. Procedure: first map the integration method — redirect to a third-party gateway, gateway embedded in an IFRAME, cross-domain form POST to the gateway, or direct card capture with backend POST to a gateway API (PCI DSS scope covers storing, *transmitting*, and processing card data — not just storage). Then attack the flow: tamper amount/quantity/currency/payment-method parameters in transit; interrupt and abandon transactions mid-flow (does an unpaid order still fulfill?); replay transaction requests; race parallel submissions on a payment or balance operation; abuse stored-card tokenization (use another token's card reference); attempt refund abuse and negative-value inputs (negative quantity/amount → credit). Interpretation: server accepting tampered amounts, completing abandoned/interrupted orders, honoring replays/races, or allowing negative values = financial-impact finding; also flag payment params processed without integrity checks (server-side recomputation or signed totals expected).

## Common findings

Negative quantity/price fields accepted; discount/coupon replay; seat/inventory held indefinitely; post-approval editing bypassing checks; hidden `admin`/`debug` params honored; step-skipping in checkout/KYC flows; `.php` (or double-extension) upload to webroot; misuse sequences never flagged.

## Escalation notes

Logic flaws chain hard: forged requests (BUSL-02) + missing integrity checks (BUSL-03) = price/privilege manipulation; upload (BUSL-08/09) → webshell → CONF-09 file-permission review; timing (BUSL-04) + race single-packet sends → balance/voucher duplication; workflow bypass (BUSL-06) + session puzzling (SESS-08) → auth/flow circumvention. Always quantify business impact in the report — "attacker pays $0.01 for $X item" beats "parameter tampering possible."
